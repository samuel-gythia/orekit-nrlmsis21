# Release Blockers & Open Decisions (`orekit-nrlmsis21` v1.0.2 RC)

This file tracks all unresolved **legal**, **licensing**, **metadata**, **repository-history**, and **technical** blockers that must be resolved before creating or publishing a public GitHub release or PyPI package.

---

## 1. Critical Legal & Licensing Blockers (Must Resolve Before Publishing)

### B1. Candidate License Not Yet Finalized (`LICENSE` Is a Working Draft)
- **Current State**: Using a permissive license (**Apache License, Version 2.0**) for independently authored wrapper components is a **candidate approach, NOT an approved legal decision**.
- **Risk**: `LICENSE` and `NOTICE` copied from the development tree already assert composite `Apache-2.0` licensing alongside `NRL-SOF-014-1`. A final `LICENSE` file must not be confirmed or published until the licensing decision and NRL questions below are resolved.

### B2. Unresolved `NRL-SOF-014-1` Section 4(b) Derivative-Work Questions
Five specific questions remain unresolved and await written clarification from **NRL Code 7630** and **NRL IP Counsel** (see inquiry draft in [`docs/NRL_CODE_7630_DELIVERY_AND_LEGAL_INQUIRY.md`](docs/NRL_CODE_7630_DELIVERY_AND_LEGAL_INQUIRY.md)):
1. **Can our Fortran `ISO_C_BINDING` interface (`native/nrlmsis21_c_api.F90`) be distributed under our own permissive license?**
2. **Does `native/nrlmsis21_c_api.F90` (which directly executes `use msis_constants`, `use msis_init`, `use msis_calc` and calls upstream NRLMSIS subroutines) — or the C header/JNI bridge coupled to it — constitute a derivative work under `NRL-SOF-014-1` Section 4(b)?**
3. **Can the C JNI bridge (`native/nrlmsis21_jni.c`), pure Java Orekit adapters (`java/`), and Python package (`python/`) be distributed independently when upstream NRLMSIS 2.1 source, `msis21.parm`, and compiled NRL libraries are excluded?**
4. **What exact notices, disclaimers, Section 4(b) Code 7630 deliveries, Open Source / U.S. Government license grants, and trademark terms (`MSIS®`) are mandatory for both a source-only wrapper repo and any downstream compiled use?**
5. **What written permission from NRL IP Counsel (and/or Office of Naval Research Counsel) is required for any commercial use or fee-based data products (Section 2 & Section 4a)?**

### B3. Commercial-Use & Data-Product Restriction Cannot Be Waived by Downstream Wrapper License
- Under `NRL-SOF-014-1` Sections 2 and 4(a), upstream NRLMSIS 2.1 is authorized **solely for research, academic, and non-profit purposes**, and users may not sell, license, or transfer for a fee the Software, derivative works, or data products generated by the Software without prior written consent of NRL IP Counsel.
- Even if pure Python/Java/C wrapper layers were cleared for `Apache-2.0`, running the integrated model requires upstream NRLMSIS 2.1. Repository documentation must never claim unrestricted commercial usability.

### B4. Precompiled Binary Wheel Redistribution Remains Prohibited Pending Clearance
- No `.whl`, `.dll`, or `.so` containing compiled NRLMSIS 2.1 object code or `msis21.parm` may be published on GitHub Releases or PyPI. (All `.dll`, `.so`, `.parm`, and binary wheels have been excluded from this preparation workspace.)

## 4. Technical & Reproducibility Blockers Before Tagging `v1.0.2`

### B7. Local Java JAR Compilation Step for Source-Only Checkout
- Because `python/orekit_nrlmsis21/lib/orekit-nrlmsis21-1.0.2.jar` and all other generated `.jar`/`.dll`/`.so` binaries are excluded from this clean preparation workspace:
  - End users checking out the repository from source must build `orekit-nrlmsis21-1.0.2.jar` (via `python build_dev.py ...`, `scripts/build_java.ps1`, or `javac --release 17` + `jar`, matching `.github/workflows/ci.yml`) before running `setup.py bdist_wheel` or importing `orekit_nrlmsis21`.
  - Confirm `MANIFEST.in` / `setup.py` expectations when creating an `sdist` vs. CI-built wrapper wheel: building `sdist` in source-only mode emits a setuptools warning or skips `lib/orekit-nrlmsis21-1.0.2.jar` unless the JAR compilation step has been run first. (Verified cleanly when Java build runs beforehand as in `.github/workflows/ci.yml`.)

### B8. Linux Python `orekit-jpype` End-to-End Parity Verification
- On Linux x86_64, CMake build, `tests/test_c_api.py` (200 reference vectors), `tests/test_user_supplied_source_and_loader.py` (`12/12`), and OpenJDK 17 direct JNI + Orekit validation (`LinuxJniValidation.java`) were verified, whereas Python-side Orekit suites (`test_cssi_adapter_verification.py`, `test_orekit_atmosphere.py`, `test_fault_injection_regression.py`, `test_batch_least_squares.py`) were skipped in the local Linux Python environment because `orekit-jpype` was only installed on Windows (Java/JNI Orekit equivalence was checked directly on OpenJDK 17 Linux). Run the full Python-Orekit suite on a Linux Conda/pip environment with `orekit-jpype` installed if full cross-platform Python-JVM symmetry is desired.

### B9. Diagnostic & Unaudited Scripts Review
- Before public tag creation, review whether auxiliary scripts in `scripts/` (e.g., `benchmark_suite.py`, `compare_atmosphere_models.py`, `compare_nrlmsis21_vs_pymsis.py`, `run_milestone*.ps1`, `download_data.py`, `setup_data.py`, `inspect_jars.py`) should all ship in the initial public release or be trimmed to core build/acquisition scripts. Note that `run_milestone1.ps1`–`run_milestone3.ps1` assume `$env:NRLMSIS21_SOURCE_DIR` or legacy `external/NRLMSIS2.1` fallback.
